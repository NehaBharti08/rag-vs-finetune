## Does the configuration caveat matter?

| Correct-section across 4 configs | 0.0% to 4.0% (spread **4.0 pp**) |
|---|---|
| Correct-act across configs | 93.0% to 93.0% (spread 0.0 pp) |
| Best config | `r16_lr2e-4` at 4.0% |
| Reported config | `r16_lr2e-4` at 4.0% |

**No configuration is materially better.** The spread across rank and
learning rate is 4.0 pp.

That spread is small in absolute terms but it is **not** below the noise,
and saying so would be sloppy: at n=100 these rates are 0 to 4 *items*,
and binomial noise alone is ~1.4-2.0 pp. The spread is a couple of
standard errors, i.e. consistent with sampling noise but not demonstrably
zero.

What settles the question is not the spread but the direction: **the best
configuration is the one already reported.** There is no better config to
switch to, so no headline number moves. And every config sits ~85 pp below
the retrieval arms, which is the comparison the project is actually about.

So the caveat was **not** load-bearing, and the finding can be stated
without it: a LoRA adapter of this size trained on 2,830 examples does not
learn a ~1,090-way section mapping, and neither 4x the adapter capacity nor
halving the learning rate changes that. It is a property of the task, not
of one configuration.

Rank 64 is the informative cell. If section recall were **capacity**-limited,
4x the adapter parameters (161M vs 40M trainable) is where it would show.
It does not - rank 64 scores 0.0% and 2.0%, straddling rank 16's 0.0% and
4.0%. That points at the data rather than the adapter.

The sharpest number in the table is the one that does **not** move at all:
**act-level accuracy is 93.0% in all four configurations**, identical to
three significant figures across a 4x change in adapter capacity and a 2x
change in learning rate. The thing fine-tuning learned here is completely
insensitive to the hyperparameters people tune, and the thing it failed to
learn is equally insensitive. Both halves of the headline are properties of
the task.
